# 面试问答卡

全部回答都对应本仓库里**真实存在**的代码与数据（含行号级别的事实），
被追问时可以直接翻文件。凡是"没做"的地方都直说没做，理由也准备好。

---

## A. 为什么是 LSM

**1. 为什么用 LSM-Tree 而不是 B+ 树？**

B+ 树是原地更新：一次随机写要改一个 4 KB 页，还可能触发页分裂；LSM 把随机写变成顺序追加
（WAL + SSTable），写吞吐高、写放大在"顺序写"这一侧更友好。代价是读要查多层，
所以需要布隆过滤器 + 块缓存 + Compaction 控制层数。

我这个项目的目标场景是"写多读少 + 单机嵌入式"，LSM 的取舍合适。
反过来说：如果场景是"读多写少、要求单次读稳定低延迟"，B+ 树更好，LSM 的 Compaction
会造成周期性抖动（我的 p999 就是被 Flush 顶起来的）。

**2. LSM 的写放大从哪来？**

三层来源：
1. 每条记录先写 WAL（1x），再在 MemTable 里存一份（内存不算盘）；
2. MemTable 满 → Flush 成 L0 文件（1x）；
3. L0→L1→L2… 每次合并都重写数据（关键项）。

分层比例 10 时，一条数据从 L1 挪到 L_n 约被重写 `log10(总数据量/单层容量)` 次。
我实测 10 万条数据后写放大 1.64x（`kestrel.write_amp`），因为数据集太小、
只发生了 L0 合并，没走到深层——所以这个数字不能当"架构极限"讲。

## B. WAL 与持久性

**3. `Put` 返回 OK 之后，机器断电数据还在吗？**

在。`Put` 的返回条件是：记录已编码进 WAL、`write()` 成功、`fsync` 成功。
所以"已 ACK" ⊆ "已落盘"。我的 `crash_test` 用 `SIGKILL` 验证了进程崩溃这一半；
断电这一半靠"CRC 校验 + 截断尾部 + 全量 MANIFEST"保证**恢复成功且不读错值**，
但我没有做过真正的断电测试（需要 dm-flakey 或 QEMU 断电），文档里写明了。

**4. 为什么 CRC 放在记录头而不是尾部？**

解析时先读 7 字节头，用 `len` 之前先校验它 ≤ `kMaxFragmentPayload`（32761）。
如果 CRC 在尾部，就必须先把可能已损坏的 `len` 当真，去读/分配一大段内存，
"损坏文件 → OOM 或越界"这条路就关不掉。CRC 在头部时，我可以直接拒绝长度非法的记录。

**5. WAL 尾部被截断了怎么办？为什么不报错？**

报错等于拒绝启动，用户数据全没了。正确做法是：只信 CRC 合法的前缀，
把文件 `Truncate` 到最后一个合法记录的末尾（`valid_size`），然后开一个新编号的 WAL 继续写。

必须**截断**而不只是忽略：不截断的话，后续追加会接在垃圾后面，下次重启从垃圾处停止，
新写的数据永远读不到——这是 WAL 实现里最容易踩的坑之一。

**6. 组提交是怎么实现的？leader/follower 谁来选？**

写请求先入 `write_queue_`，第一个发现"当前没有 leader"的线程把自己设为 leader，
其余线程作为 follower 等结果。leader 一次取走队列里所有请求：

- 一次 `mu_` 临界区里为整批分配 seq、批量插 MemTable；
- 整批编码进**一个** buffer，调用一次 `log_->Append()` → 一次 `write` + 一次 `fsync`；
- 逐 writer 发布 `done` 并唤醒。

实测：8 线程平均批大小 3.35，吞吐 2425 ops/s，`2425 ÷ 3.35 ≈ 724` 次 fsync/s，
乘 1.38 ms ≈ 1.00 s/s —— 磁盘完全打满，说明批处理确实生效而不是"队列在跑、仍各刷各的盘"。

**7. follower 为什么先自旋再睡？**

因为批处理只有几微秒，而"睡下→被唤醒"在本机要 50~120 µs。纯条件变量的实测结果是
4 线程写 48k ops/s，比单线程的 324k 还慢（队列把 fsync 串行化了，却把唤醒开销乘上了线程数）。
加 8192 轮 `pause` 自旋后变成 351k（4 线程）/ 391k（8 线程）。
自旋窗口必须覆盖"一批的处理时长"，窗口给 2048 轮时 8 线程又退化到 82k。

**8. 为什么 `notify_one` 要在持有 `w->mu` 的时候调用？**

因为 follower 的 `Writer` 是**调用方栈上的对象**。leader 发布 `done` 之后，如果 follower
立刻返回并销毁对象，而 leader 还在 `notify_one(w->cv)`，就是 use-after-free。
在 `w->mu` 内发布并唤醒、且 follower 观察到 `done` 后必须再拿一次 `w->mu` 才返回，
就保证了"leader 已经离开临界区"先于"follower 销毁对象"。
这个 bug 在 4 线程基准里稳定崩溃，不是理论风险。

## C. 内存层与 MVCC

**9. 内部键为什么把 seq 编码进 key？**

内部键 = `user_key + 8 字节 (seq << 8 | type)`，比较器对后缀按 seq **降序**解析。
这样同一个 user_key 的所有版本在跳表和 SSTable 里天然相邻且"新→旧"排列，
读的时候"第一个 `seq <= snapshot` 的版本"就是可见版本——快照读和墓碑共用同一套判断，
不需要额外的版本链或索引。

**10. 快照读怎么实现？为什么不直接传一个数字？**

`GetSnapshot()` 返回一个冻结的序列号对象，`ReadOptions::snapshot` 拿它去查。
之所以要**显式持有**（而不是让用户随便传个数）：Compaction 需要知道"还有没有读者可能在看旧版本"，
`smallest_snapshot = min(活跃快照)` 就是它可以丢弃旧版本的下界。
不持有快照的读者无法阻止 Compaction 清理，所以 API 设计上强制成对出现
（`GetSnapshot` / `ReleaseSnapshot`），忘记释放的代价是磁盘空间不被回收。

**11. 墓碑什么时候能真正删掉？**

只有在"比它更旧的版本已经不可能存在"时。我的判据是：归并时遇到某个 user_key 的
`seq <= smallest_snapshot` 的版本之后，该 key 更早的版本全部丢弃；
墓碑本身只有在最底层合并（不再有更旧层）时才删除。

这里有个经典 off-by-one：必须是 `<=` 而不是 `<`。快照号 N 必须能看到 `seq == N`
那个版本本身，用 `<` 会把快照自己该看到的数据删掉。

**12. 跳表的并发怎么做？为什么不用无锁队列？**

写入由 `DBImpl::mu_` 串行化（单写），读是并发的多读：新节点的 `next` 指针用
`memory_order_release` 发布，读者用 `acquire` 读取。因为节点在 MemTable 生命周期内
从不释放，不存在 ABA 和回收问题，也就不需要 hazard pointer / epoch。
这比"全无锁跳表"简单得多，而写入本来就要串行分配 seq，无锁没有收益。

## D. SSTable 与读路径

**13. 前缀压缩 + 重启点解决什么问题？**

块内相邻 key 前缀高度重复（比如 `user:0001`、`user:0002`），每条只存"与上一条的
公共前缀长度 + 剩余部分"（`shared_len / non_shared_len / key_delta`），空间能省一半以上。

但纯前缀压缩没法随机查找（不从头解就不知道完整 key）。所以每 16 条设一个**重启点**：
该条存完整 key，块尾存重启点偏移数组。查找时先二分重启点，再线性扫最多 16 条。
顺序扫描 O(1)/条，随机查找 O(log(重启点数) + 16)。

**14. 一次 `Get` 的完整路径？**

MemTable（跳表二分）→ L0 文件（新到旧逐个查）→ L1..L6（每层按 key 范围过滤，最多 1 个文件）。
每个 SSTable 内部：布隆过滤器（不存在直接返回，不碰磁盘）→ 索引块二分 → 读数据块
（先查块缓存）→ 块内二分重启点 + 局部扫描 → 校验 type。
命中墓碑立即返回 `NotFound`，**不能继续往下层读**，否则会读到被删除的旧值——这是"读错值"的最常见来源。

**15. 布隆过滤器的参数怎么选？**

每 key 10 bit，`k = 10 × ln2 ≈ 7` 个探测，理论误判率约 1%。双哈希（`h1 + i*h2`）派生
k 个位置，省掉 k 次哈希。实测 `read_miss` 3.3M ops/s（p50 0.1 µs）对 `read_hit` 112k ops/s，
差 30 倍，说明过滤器确实把绝大多数无效读挡在了磁盘之外。

关键的保守选择：过滤器缺失/损坏时 `MayContain` 返回 **true**（宁可多查一次盘，也绝不能漏）。
漏判 = 读到"不存在"，就是数据错误。

**16. 索引项 key 存的是什么？为什么？**

存该数据块**最后一个内部键**。查找时在索引块里二分要找的 key：
第一个 `索引key >= seek_key` 的块就包含目标（或目标不存在但落在这个块的范围里），
于是定位一次就够，不需要前后两块都读。

## E. Compaction 与工程取舍

**17. Compaction 什么时候触发？为什么不许并发合并？**

- L0 文件数 ≥ 4 → 合并 L0 全部 + L1 全部 → 输出 L1；
- 否则按层容量 `base × 10^(L-1)` 判断（base 8 MiB，7 层）。

只允许一个合并：并发合并要引入"多版本 + 输入文件引用计数 + 输出文件区间不重叠"的约束，
正确性成本远高于收益（尤其在单盘上，并发合并只会让 IO 更碎）。我的做法是
归并阶段不持 `mu_`，只在最后换元数据时短临界区，读请求几乎不受影响。

**18. MANIFEST 为什么用全量快照，而不是 LevelDB 的增量 VersionEdit？**

增量方案需要：编解码 + 重放状态机 + 定期全量重写（否则无限增长）。
全量方案每次 O(文件数)，几十行文本、几 KB，写一次 rename 生效。
**用一点写放大换掉一整块最容易出隐蔽 bug 的状态机**，对一个月工期的项目是正确的取舍。
如果文件数上千（大集群），这个选择就不成立了。

**19. 怎么保证"文件写入的原子性"？**

所有 `*.sst` / `MANIFEST` 都是：写 `.tmp` → `Flush` → `Sync`（数据落盘）→ `rename`
→ `SyncDir`（目录项落盘）。顺序不能变：rename 之前必须 Sync，否则崩溃后可能 rename 成功
但文件内容是空的。启动时目录里的 `.tmp` 和不在 MANIFEST 里的 `.sst` 一律当孤儿忽略。

**20. 你怎么发现"4 线程读比单线程还慢"的？**

先跑基准，发现 `read_hit` 4 线程 110k ops/s ≈ 单线程 109k（完全不扩展）。
读代码发现 `Get` 用了 `std::lock_guard<std::mutex> mu_` 排他锁。
改成 `shared_mutex` + `shared_lock` 后 4 线程 410k、8 线程 757k。
这件事的教训写进了流程：**每个优化点都要有 before/after 的数字**，
纯靠"我觉得这样更快"改代码，很可能改错方向（写队列的自旋窗口就是反例：
不加自旋时队列反而让写变慢 6 倍）。

## F. 追问：如果继续做

**21. 现在最该优化的三件事？**

1. **Flush 停顿**：p999 是 p50 的 3 倍，根因是 Flush 在排他锁内写整个 SSTable。
   做法：MemTable → Immutable 队列，后台线程写盘，写线程只做"换指针"。
2. **读路径持锁做 IO**：慢读者会挡住 Flush/写。做法：Version 引用计数，
   读路径拿 version 引用后释放 `mu_` 再读盘。
3. **公开 Iterator**：现在只有点查，缺 `NewIterator` + 归并迭代器 + 快照过滤，
   没有它就没法做范围扫描，也就没有 CLI。

**22. 如果要支持"同一目录多进程打开"，需要做什么？**

加 `LOCK` 文件 + `fcntl(F_SETLK)` 排他锁（Windows 用 `LockFileEx`），
持有到进程退出。现在没做，两个进程同时打开同一目录会互相破坏——这是我文档里
明写的已知缺陷，不掩饰。

**23. 这个项目最大的技术风险是什么？**

不是性能，是**崩溃一致性**。LSM 的恢复路径涉及 WAL 截断、MANIFEST 原子替换、
孤儿文件处理三者交叉，任何一处顺序错都会变成静默数据损坏。
应对方式：把每条不变量都写成测试（`test_recovery` 的四个用例 + `crash_test` 三种模式），
并且断言"可见数据必须是写入序列的前缀"——这条比"数据都在"更能抓住细微的顺序错误。
