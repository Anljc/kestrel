# 基准测试报告

所有数字都是在本机跑出来的，命令和原始数据都在仓库里（`docs/bench_ext4.csv`、
`docs/bench_tmpfs.csv`、`benches/run_all.sh`）。表格里的数字可以按 §2 的命令原样复现。

---

## 1. 环境

| 项 | 值 |
| --- | --- |
| CPU | AMD Ryzen 7 7735H（8 核 16 线程，WSL2 分配 16 vCPU） |
| 内存 | 16 GB（WSL2 上限约 3.8 GB 用于 tmpfs） |
| 内核 | 6.6.87.2-microsoft-standard-WSL2 |
| 编译器 | g++ (Ubuntu 15.2.0) 15.2.0 |
| 构建 | `RelWithDebInfo`（`-O2 -g`），CMake + Ninja |
| 数据目录 A | `/home/<user>/kestrel_bench`，ext4（`/dev/sdd`，虚拟磁盘） |
| 数据目录 B | `/tmp/kestrel_bench`，**tmpfs（内存盘）** |

### 1.1 先量 fsync：它决定了一半的结论

`write(128B) + fsync` 循环 2000 次的实测均值：

| 文件系统 | 单次 write+fsync |
| --- | --- |
| tmpfs（`/tmp`） | **1.7 µs** |
| 9p（`/mnt/d`，Windows 盘） | **659 µs** |
| ext4（`~`） | **1358 µs** |

所以：

- **基准目录绝不能放在 `/tmp`**。在 tmpfs 上 fsync 是个空操作，"同步写"退化成
  "写内存 + 更新跳表"，组提交自然一点收益也测不出来（见 §5 的对照）。
- ext4 上 1.36 ms/次 fsync 意味着：单线程同步写的理论上限就是 **~735 ops/s**，
  实测 752 ops/s —— 写路径本身几乎不花时间，全部时间都在等盘。
- 这台机器（WSL2 虚拟磁盘、未关 barrier）比常见 NVMe（50~200 µs/fsync）慢一个数量级。
  换到真机上，组提交的收益会更小（因为单次 fsync 变便宜），但结论方向不变。

## 2. 方法

```bash
# 全量：构建 + 单测 + 基准（结果写 docs/bench_ext4.csv）
OPS=8000 READ_OPS=4000 bash benches/run_all.sh

# tmpfs 对照
OPS=100000 READ_OPS=50000 BENCH_DIR=/tmp/kestrel_bench \
  OUT_CSV=docs/bench_tmpfs.csv bash benches/run_all.sh
```

场景定义（`tools/db_bench.cpp`）：

| 场景 | 操作 | 说明 |
| --- | --- | --- |
| `seq_write` | `Put` 连续编号的 key | 同步写（返回即已 fsync），衡量写路径 + 组提交 |
| `rand_write` | `Put` 随机 key（80% 落在已写区间） | 产生多版本，给 Compaction 制造活干 |
| `read_hit` | 先灌数据并 `Flush`，再随机读已存在的 key | 衡量点查 + 块缓存 |
| `read_miss` | 读一定不存在的 key | 衡量布隆过滤器的有效性 |
| `recovery` | 写入 N 条后关闭，重新 `DB::Open` | 只计 `Open` 的耗时（含 WAL 重放） |

口径说明（这几条直接影响数字能不能信）：

1. **延迟分位数**：每个操作单独记纳秒，排序后取 p50/p99/p999。不是"总时间/次数"。
2. **写放大**：`(flush 写出字节 + compaction 写出字节) / 用户写入字节`，
   在**计时结束后**才触发 `Flush` 并取值——否则数据还躺在 MemTable 里，
   分子为 0 而分母已计入，会算出 0.7 这种假数。
3. **读场景的灌数不计时**：先写满再计时，避免把写延迟混进读吞吐。
4. 每个场景独立进程、独立目录（脚本每次重置），避免上一次的页面缓存/层数影响下一次。

## 3. 结果：ext4（真实磁盘，fsync ≈ 1.36 ms）

原始数据：[`docs/bench_ext4.csv`](bench_ext4.csv)

| 场景 | 线程 | ops/s | p50 | p99 | p999 | 批大小 |
| --- | --- | --- | --- | --- | --- | --- |
| seq_write | 1 | 752 | 1.30 ms | 1.71 ms | 2.74 ms | 1.00 |
| seq_write | 2 | 748 | 2.64 ms | 3.20 ms | 5.03 ms | 1.00 |
| seq_write | 4 | 1,046 | 2.56 ms | 3.13 ms | 4.80 ms | 1.41 |
| seq_write | 8 | **2,425** | 1.50 ms | 3.12 ms | 4.39 ms | **3.35** |
| rand_write | 1 | 754 | 1.30 ms | 1.67 ms | 3.13 ms | 1.00 |
| rand_write | 4 | 1,039 | 2.58 ms | 3.15 ms | 5.15 ms | 1.40 |
| read_hit | 1 | 112,390 | 8.2 µs | 18.6 µs | 40.8 µs | – |
| read_hit | 2 | 221,628 | 8.3 µs | 16.6 µs | 35.6 µs | – |
| read_hit | 4 | 389,793 | 8.4 µs | 20.4 µs | 36.7 µs | – |
| read_hit | 8 | **700,466** | 8.6 µs | 21.3 µs | 54.7 µs | – |
| read_miss | 1 | 3,348,796 | 0.1 µs | 0.3 µs | 0.8 µs | – |
| read_miss | 4 | 4,522,518 | 0.2 µs | 0.4 µs | 1.8 µs | – |
| recovery（8000 条） | 1 | 0.52 ms（总） | – | – | – | – |

### 3.1 写：吞吐就是 fsync 次数

把两个数字对起来看：

```
8 线程：2425 ops/s ÷ 3.35 条/批 ≈ 724 次 fsync/s
        724 × 1.38 ms ≈ 1.00 s/s      -> 磁盘 100% 饱和，没有别的浪费
1 线程：752 ops/s × 1.33 ms ≈ 1.00 s/s -> 同上
```

也就是说写路径的**有效工作（跳表插入、编码、WAL 追加）几乎不占时间**，
吞吐完全等于 `1 / (fsync 时间 / 每批条数)`。所以：

- 8 线程相对单线程 **3.2x**，恰好等于平均批大小 3.35 → 组提交是唯一有效的杠杆。
- 2 线程时批大小仍是 1.00：第二个请求在 leader 做 fsync 的那 1.3 ms 里到达，
  只能进下一批。**批大小随并发升高而变好，但不会凭空出现**——这是"不主动延迟攒批"
  的组提交的固有形态（不额外引入延迟，因此也不牺牲延迟）。
- p50 从 1 线程的 1.30 ms 涨到 8 线程的 1.50 ms：一点队列延迟换来 3.2x 吞吐。

### 3.2 读：8 线程 6.2x

- `read_hit` 单次 8.2 µs（块在缓存里），8 线程 700k ops/s，接近线性。
  关键改动是 `mu_` 用 `shared_mutex`，读路径拿共享锁：**读读不互斥**。
  早期版本用独占 `mutex`，4 线程读只有 110k ops/s（比单线程还低），是本项目里
  最典型的一次"基准先发现、代码后修"的回归。
- `read_miss` 3.3M ops/s、p50 0.1 µs：布隆过滤器命中"不存在"判断后直接返回，
  一次磁盘 IO 都不做。与 `read_hit` 相差 30 倍，这就是过滤器的价值。

### 3.3 为什么 p999 是 4.4 ms 而不是 1.4 ms

尾部延迟来自 **Flush 停顿**：`write_buffer_size = 4 MiB` 写满时，写线程要在
`write_lock_` 排他锁下写完整个 SSTable 并 fsync，期间所有写请求排队。
8 线程 8000 条 × ~140 B ≈ 1.1 MB，刚好卡在阈值附近，偶发一次 Flush 就把 p999 顶到 4 ms。
这是当前"无 Immutable 队列、Flush 串行"设计的直接代价，见 `docs/DESIGN.md` §12。

## 4. 结果：tmpfs（fsync 免费时的另一种瓶颈）

原始数据：[`docs/bench_tmpfs.csv`](bench_tmpfs.csv)。数据集 10 万条写入 / 5 万条读。

| 场景 | 1 线程 | 4 线程 | 8 线程 |
| --- | --- | --- | --- |
| seq_write（ops/s） | 324,420 | 351,925 | 391,524 |
| rand_write（ops/s） | 289,491 | 321,076 | – |
| read_hit（ops/s） | 109,485 | 410,122 | 757,131 |
| read_miss（ops/s） | 2,429,828 | 6,904,066 | – |
| 写放大（10 万条后） | 1.64x | | |
| 缓存命中率（read_hit） | 0.95 | 0.95 | 0.97 |
| 恢复（10 万条重放） | 8.0 ms | | |

这张表和 §3 的对比正好说明了基准的意义：

- fsync 从 1.36 ms 降到 1.7 µs 后，写吞吐涨了 **430 倍**，但**只扩展到 1.2x**。
  因为瓶颈转移到了"一次 `mu_` 临界区里批量插跳表 + 单条 WAL 追加"的串行段上——
  组提交省下的 fsync 在这里已经不存在了。
- 结论不是"哪个实现更好"，而是：**先测出 fsync 成本，再决定要不要做组提交**。
  如果一开始只在 tmpfs 上跑，会得出"组提交无用、并发写还变慢"的错误结论。

### 4.1 自旋窗口的效果（follower 等待策略）

fsync 免费时，批处理只有几微秒，follower 若直接睡进条件变量，
"睡下→被唤醒"的往返（本机实测 50~120 µs）比批处理本身贵一个数量级。实测三档：

| follower 等待策略 | 4 线程 seq_write（tmpfs） | 8 线程 |
| --- | --- | --- |
| 纯条件变量 | 48,781 ops/s | – |
| 自旋 512 轮 | 78,466 ops/s | – |
| 自旋 2048 轮 | 339,327 ops/s | 82,081 ops/s |
| **自旋 8192 轮（当前）** | 351,925 ops/s | 391,524 ops/s |

（2048 轮在 8 线程下崩到 82k：批处理变长后自旋窗口不够，又退化成睡眠。
这条曲线说明窗口必须覆盖"一批的处理时长"，而不是拍一个固定值。）

## 5. 故障注入结果

### 5.1 进程强杀（`tools/crash_test.cpp`）

子进程持续 `Put`，每成功一条就往 ack 文件追加一行（`fflush` 到内核），
父进程在 40~150 ms 的随机时刻 `SIGKILL`；重启后逐条核对：

| 环境 | 轮数 | 已 ACK 写入 | 丢失 | 值错误 | 恢复耗时 |
| --- | --- | --- | --- | --- | --- |
| tmpfs | 100 | 694,759 | **0** | **0** | 最大 61 ms |
| ext4 | 30 | 1,875 | **0** | **0** | 最大 0.45 ms |

判定标准是三条同时成立：`wrong_value == 0`、`unexpected_error == 0`、
可见数据构成写入序列的**前缀**（不出现"后面的 key 在、前面的丢了"的洞）。

**边界要讲清楚**：`SIGKILL` 只验证"进程崩溃"，不验证"机器断电"——数据此时已在
内核页缓存里，进程死掉不会丢。断电场景靠 §5.2 的文件级破坏来近似（torn write）。

### 5.2 WAL 截断 / 字节翻转（`crash_test --mode truncate|bitflip`、`test_recovery`）

| 注入方式 | 期望 | 实测 |
| --- | --- | --- |
| WAL 随机位置截断 | 恢复到最后一个 CRC 合法的记录，不得报 Corruption 退出 | PASS |
| WAL 随机字节翻转 | 定位到该记录，之后的数据全部丢弃，且不得读出错误值 | PASS |
| 数据已 Flush 后破坏 WAL | SSTable 里的数据必须完好 | PASS |
| 目录里出现孤儿 `.sst`（未记入 MANIFEST） | 忽略，不得当成数据 | PASS |

判定标准写成**不变量**，而不是"必须丢多少条"：

1. 恢复必须成功（报 Corruption 退出 = 数据全丢）；
2. 不得读出错误 value，不得出现 `NotFound` 之外的错误；
3. 可见数据必须是写入序列的前缀（不允许中间空洞）。

为什么不拿"丢了 N 条"当判据：被切断的位置可能落在一条**尚未 ACK** 的记录上
（`kill` 恰好发生在 `fsync` 完成与写 ack 之间），此时 `missing = 0` 反而是最好的结果。
早期版本把 `missing == 0` 判为失败，实测约 1/10 轮误报——这是测试工具的 bug，不是引擎的。
现在改为输出 `damaged` 字节数与 `missing` 观测值，并用"注入必须真的改动过文件"
来防止空转；"必须丢数据"这类确定性场景由 `test_recovery` 的四个用例覆盖。

另外 `test_recovery` 会断言"破坏后二次打开视图一致"（幂等），
防止出现"第一次恢复成功、第二次恢复出别的结果"这种隐蔽错误。

## 6. 结论（可直接当面试回答）

1. **写路径的瓶颈是被测量的，不是猜的**：本机 fsync 1.36 ms，单线程同步写 752 ops/s，
   理论上限 735 ops/s，误差 2% —— 说明写路径本身没有明显浪费。
2. **组提交是唯一有效的写吞吐杠杆**：8 线程批大小 3.35，吞吐 3.2x，且
   `吞吐 × fsync 时间 ≈ 100%`，磁盘被打满，没有额外开销。
3. **不主动延迟攒批**：批大小随并发自然增长，不牺牲单条写延迟。
4. **读扩展靠共享锁**：点查 8 线程 6.2x；改成独占锁后 4 线程就会负扩展（实测过）。
5. **布隆过滤器把"不存在"的读变成内存操作**：3.3M ops/s vs 命中 112k ops/s。
6. **尾部延迟来自 Flush 停顿**：p999 ≈ 3~4x p50，根因是 Flush 在排他锁内做完整 SSTable 落盘。

## 7. 这份基准的局限

- 单机、单盘、**单进程**，不能外推到多盘/多机。
- WSL2 的虚拟磁盘 fsync 成本（1.36 ms）比裸机 NVMe 高一个数量级，
  绝对吞吐不可直接对比 LevelDB/RocksDB 的公开数据；可比的只有"扩展性形状"。
- 数据集很小（ext4 场景 8000 条、tmpfs 场景 10 万条），L1 以上基本没参与，
  Compaction 的写放大没有充分暴露；写放大 1.64x 是 10 万条 + 默认阈值下的单点值。
- 延迟分位数来自单次进程内的样本，没有做多轮取中位数，抖动约 ±10%。
- 没有对比基线（LevelDB/RocksDB）：本报告只回答"这套实现自身的瓶颈在哪"，
  不回答"比 LevelDB 快还是慢"。
